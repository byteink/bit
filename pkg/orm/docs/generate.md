# Generate migrations from your entities

You add a `phone` field to your `Widget` class, ship the code, and forget
the database still has no `phone` column - nothing caught it, because
nothing compares your entities against the live schema. Or you remember,
and hand-write the `ALTER TABLE` yourself, one column name away from what
the entity actually declares. Or, worse, you rename a column by
hand-writing a migration that drops the old one and adds the new one -
guessing that a drop next to an add is really one rename is exactly the
kind of guess that destroys the dropped column's data when it's wrong.

`generate` closes that gap the other direction: it reads what your
database actually looks like, diffs it against the entities you give it,
and writes a `.bit` file with the `alter()` calls to close the
difference - for you to read, edit if it guessed wrong, and commit.

## The simplest thing that works

```bit
import { Data, ServerDialect, TableEntity, generate, generateInto } from "orm"
import { AttrDesc, FieldDesc } from "std/sql"

@table("widgets") class Widget {
  @id
  id: i64
  name: string
  phone: string
  @enumVariants("Draft", "Active", "Archived", "Retired")
  status: string
}

fn regenerate(db: Data): string! {
  return generate(db, [Widget{}], "add_widget_phone", ServerDialect.Postgres)?
}
```

`Widget{}` needs no `implements TableEntity` clause - `@table` synthesizes
exactly the two members `TableEntity` asks for (`tableDescriptor()` and
`tableAttrs()`), and Bit's structural typing (SPEC section 12.3's
bare-literal rule) is what lets a plain `[Widget{}]` literal convert to
`[]TableEntity` at the call site.

`ServerDialect.Postgres` names which server `db` is - `generate` never
asks the live connection what it is (see [Dialect](dialect.md) for why),
so you supply it explicitly the same way `upsert` and `forUpdate` already
ask. Most of what `generate` writes doesn't care, but one finding does: an
enum column's drifted CHECK constraint (below) renders one engine's own
SQL keyword, and `generate` has to know which.

Say the live `widgets` table has `id`, `name` and a `status` already
matching every variant `Widget` declares, but not yet `phone`.
`regenerate(db)` reads that, diffs it against `Widget`'s own fields, and
writes `migrations/0007_add_widget_phone.bit` (the number is one higher
than whatever is already in the directory):

```text
// Generated by orm.generate("add_widget_phone") - review before committing.
// A dropColumn next to an addColumn in the same block may be a
// rename; this generator never guesses one - edit it into a
// renameColumn(...) call if that is what you meant.

import { alter } from "orm"

export fn up() {
  alter("widgets", (t) => {
    t.addString("phone", 255)
  })
}
```

`generateInto` is the same function taking the output directory as its own
argument instead of the hardcoded `"migrations"` - reach for it when a
caller (this package's own tests, or a script iterating several projects)
needs to point somewhere other than the current directory's `migrations/`:

```bit
fn regenerateInto(db: Data, dir: string): string! {
  return generateInto(db, [Widget{}], "add_widget_phone", dir, ServerDialect.Postgres)?
}
```

## Growing it: more than one entity, and a real diff

A real call site passes every entity that might have drifted, not just
one - `generate` diffs each independently and writes them into the same
file:

```bit
@table("orders") class Order {
  @id
  id: i64
  widgetId: i64
  quantity: i64
}

fn regenerateAll(db: Data): string! {
  return generate(db, [Widget{}, Order{}], "sync_schema", ServerDialect.Postgres)?
}
```

If `orders` already matches `Order` exactly, nothing is written for it -
only `widgets`' diff appears in the file. If every entity already matches
the live schema, `generate` writes no file at all and says so:

```text
pkg/orm: generate: schema already matches every entity given; nothing written
```

That refusal matters as much as the file it writes the rest of the time -
a `migrations/` directory full of empty files is how people stop reading
them.

## An enum's variant list drifts too

Adding or removing a column is not the only way `Widget` and the live
schema disagree. `status` above declares
`@enumVariants("Draft", "Active", "Archived", "Retired")` - the same
"caller supplies the list, Bit has no reflection" list [Enum
columns](enum.md) already asks for, now recorded on the field itself so
`generate` can read it back. Picture the team having shipped `Widget`
with only three variants at first, so the live CHECK constraint still
reads `status in ('Draft','Active','Archived')` - the column is present
either way, same name, same type, so the add/drop diff above sees
nothing at all. `regenerate(db)` catches it anyway:

```text
alter("widgets", (t) => {
  t.raw("alter table \"widgets\" drop constraint \"widgets_status_check\", add constraint \"widgets_status_check\" check (status in ('Draft','Active','Archived','Retired'));")
})
```

That `t.raw(...)` call is [enumCheckAlter](enum.md)'s own rendered SQL,
dropped in verbatim - the one finding `generate` ever renders one
engine's literal DDL for, because a CHECK swap has no dialect-neutral
`AlterTable` op to build instead (see `ServerDialect.Postgres` above:
this is exactly what it is for). **Reordering the same three variants
writes nothing** - `enumVariantsChanged`'s SET comparison, the identical
rule `Enum columns` states, applies here too, so resorting `Widget`'s own
declaration for readability never produces a migration.

## The five rules this never breaks

Every one of these is "do not guess", because a migration is the one place
in an ORM where a wrong guess deletes data.

1. **A rename is never inferred.** A column the entity has and the
   database doesn't, and a column the database has and the entity
   doesn't, are always two separate findings - an `addColumn` and a
   `dropColumn`, never a `renameColumn`. Nothing here can tell a rename
   apart from an unrelated drop-and-add, and guessing wrong deletes the
   dropped column's data.
2. **It never applies anything.** `generate`/`generateInto` write a file
   and return a message describing it. Nothing here opens a transaction
   or runs a statement against `db` beyond the read-only query that reads
   the live schema.
3. **Entities are an explicit argument.** Bit has no reflection, so there
   is no way to enumerate "every `@table` class" on your behalf - the list
   you pass is the whole source of truth. A forgotten entity is a missing
   line in a five-line list, not a silent gap.
4. **An empty diff writes nothing**, and the message says so - see above.
5. **A destructive change is always emitted, never silently dropped from
   the output**, marked in a comment. When the same table also gained a
   column in the same pass, the comment names it too:

```text
alter("widgets", (t) => {
  t.addString("new_name", 255)
  // destructive: 'old_name' exists in the database but not in the entity; dropping it deletes data - this same diff adds 'new_name' to this table; if this is a rename, edit these two calls into one renameColumn(...) call instead
  t.dropColumn("old_name")
})
```

That comment is the whole answer to rule 1's gap: `generate` cannot tell
you renamed `old_name` to `new_name`, but it can show you both findings
next to each other so you can turn them into one `renameColumn(...)` call
yourself, which is a decision only you can make correctly.

## The sharp edge: `@table` needs an explicit name

```bit ignore
@table class Bare {
  @id
  id: i64
}
```

Passing `Bare{}` to `generate` fails loudly instead of guessing a table
name:

```text
pkg/orm: generate: this entity has no explicit @table("name") - generate cannot derive a default table name without the class's own name, which @table's synthesized members do not carry (Bit has no reflection); add an explicit @table("...") to the entity
```

[Naming](naming.md) shows `tableName` deriving a default from the class
name when `@table` carries no override - but that function takes the
class name as its own argument. `generate` never gets one: `@table` only
synthesizes `tableDescriptor()` and `tableAttrs()`, and neither carries
the class's own name as data, so there is nothing in a bare `Widget{}`
value for `generate` to read a name off. Every entity you pass it needs
its own explicit `@table("...")`.

## When not to use this

`generate` never applies a migration - it only writes the reviewed file.
Running the file it wrote against a real database is
[Migrate](migrate.md)'s job.
