# Pending release notes

Hand-written entries destined for the **next cut release's** `NOTES.md` --
for information `dist/changelog.sh` cannot produce on its own. Most often
that is a security-relevant fix whose impact needs prose (which versions are
affected, what a user would observe), not the one-line conventional-commit
summary the generator emits per commit.

## Why this file exists

`dist/out/NOTES.md` is fully generated by `dist/changelog.sh` on every
`dist/release.sh` run, and `dist/out/` is gitignored, so nothing written
directly into `NOTES.md` survives past the release that produced it. Before
this file there was no tracked, durable home for a hand-written note, and
that is exactly why the #3208 disclosure below missed both the 0.1.21 and
the 0.1.22 release notes (see #3213) even though the fix itself had already
shipped in 0.1.21.

## How to use this file

**The fold-in half is automatic (#3392).** `dist/release.sh` reads this file
right after `dist/changelog.sh` writes `dist/out/NOTES.md`, and if it finds
any entries below the `---` separator, appends each one (heading demoted one
level, under the version title) to `dist/out/NOTES.md` — on both a real run
and `--dry-run`. It prints an unmissable reminder when it does this.

**The clear-out half is deliberately still manual.** `dist/release.sh` only
ever produces a **draft**; nothing it does is visible until a human presses
publish, and a draft can be abandoned or re-cut. If clearing this file
happened automatically at generation time, an abandoned draft would silently
eat the disclosure with nothing left to fold into the release that actually
ships it. So: once a release carrying a folded entry is **published**,
delete that entry from this file (everything between `---` and the next
entry, or the whole tail if it was the only one) in the commit that records
the release notes were published. An entry that has shipped in a published
release's notes must not still be sitting here afterward.

**An entry must not start a line with `- ` or `* `.** The release skill's
"check the generated notes are complete" step asserts that
`grep -cE '^[-*] ' dist/out/NOTES.md` equals the non-merge commit count for
the release range (`dist/release.sh`'s own accounting guard in
`dist/changelog.sh` enforces the same thing for the generated bullets). A
hand-written top-level bullet would inflate that count and read as though a
real commit's bullet had been silently displaced. Use a heading and prose
instead, as the entry below does. `dist/release.sh` refuses to fold an entry
that violates this rather than let it corrupt the count silently.

## TLS-over-QUIC handshake transcript could alias a buffer the CRYPTO reassembler still owned

**Affects every release up to and including 0.1.20.** Fixed in 0.1.21 by
#3208 (commit `9199f5ba`). This disclosure was omitted from both the 0.1.21
and the 0.1.22 release notes and is being published in the first release cut
after this entry lands.

The TLS handshake code (server: `srvNegotiate`; client:
`tlsClientStartExts`) aliased the incoming ClientHello buffer directly into
the handshake transcript with a plain assignment, instead of copying it. On
the QUIC transport, that buffer is a live subslice of the QUIC CRYPTO-stream
reassembler's own backing array, not a copy. The next byte the TLS code
appended to the transcript could then grow into the reassembler's spare
capacity in place, corrupting bytes the reassembler still needed for later
CRYPTO-frame overlap checks.

**Observable symptom:** a retransmitted CRYPTO fragment that should be
accepted as identical to one already buffered is instead rejected:

```
RETRANSMIT REJECTED: quic: overlapping CRYPTO data does not match
```

No evidence of exploitability beyond this corruption was established -- only
that a buffer the QUIC reassembler still owned could be silently overwritten
by the TLS handshake code sharing it. Silent data corruption in a
security-relevant path, not a cosmetic bug: anyone running a `bit`
TLS-over-QUIC server or client on 0.1.20 or earlier should upgrade to 0.1.21
or later.
